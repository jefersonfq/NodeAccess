  Pontos avaliados

  1. Remover grupo do cadastro do Host
     Sim. Eu removeria ou esconderia groupId do formulário principal do host. Grupo não deve mais parecer destino/segmentação do host. Se ainda existir bastion herdado por
     grupo legado, isso precisa virar “legado” ou migrar para configuração direta do host/pasta.

  2. Sem pasta/ACL definida e pasta raiz
     Todo host deve estar em algum nó da árvore corporativa. Se não escolher pasta, cai na Raiz do inventário. Mas a UI deve deixar claro: “Este host herdará as permissões
     da raiz”. Nada de “sem ACL”.

  3. Relacionar host à Pasta/ACL
     No cadastro/edição do host deve existir campo obrigatório ou padrão:
     Pasta do inventário corporativo
     com default Raiz do inventário. Isso substitui o papel antigo de grupo/escopo para acesso.

  4. Escopo deixa de fazer sentido
     Concordo. personal/team/global não deve mais ser apresentado como regra de acesso. Pode continuar internamente durante migração, mas a UI nova deve esconder isso ou
     tratar como legado.

  5. Nível de execução
     Isso não é ACL. Execução deve ser configuração/política do host ou de comando/sessão. Exemplo: permite terminal interativo, SFTP, túnel, snippets, comandos bloqueados
     etc. ACL diz “quem pode”; política do host diz “o que tecnicamente pode fazer”.

  6. Permissões do host vs ACL
     Separação sugerida:
      - ACL: Visualizar, Conectar, Editar, Administrar permissões.
      - Host: protocolo, IP, porta, usuário SSH, autenticação, bastion, PEM, 1Password, políticas de execução.
        A permissão Editar da ACL permite alterar configuração do host. Mas a configuração do host não concede acesso por si só.

  7. Clareza para usuário
     Precisamos ajustar microcopy:
      - “Permissões de acesso” = ACL.
      - “Configurações de conexão” = dados técnicos do host.
      - “Políticas de execução” = limites operacionais.
        Evitar chamar tudo genericamente de “permissões”.

  8. ACL da raiz
     A raiz deve ter ACL administrável. Ela define o acesso padrão de tudo que estiver diretamente abaixo dela ou sem pasta específica. Minha recomendação: raiz começa sem
     Connect amplo. Idealmente só admins têm Admin; grupos recebem acesso em pastas específicas.

  9. Precedência
     ACL deve ser porta de entrada obrigatória.
     Fluxo:
      1. Sem View: host não aparece.
      2. Com View, sem Connect: aparece, mas ações de conexão bloqueadas.
      3. Com Connect: pode conectar, se o host estiver tecnicamente configurado.
      4. Com Edit: pode alterar configuração do host.
      5. Com Admin: pode alterar ACL.

     Configuração do host nunca deve “dar acesso” se a ACL negar.

  10. Mostrar ACLs e permissões por pasta/host/usuário
     Sim, precisamos três visões:

  - Pasta: quem tem acesso nesta pasta e o que herda.
  - Host: permissões efetivas neste host e configuração técnica.
  - Usuário: quais acessos ele tem e de onde vieram.

  Sim. A melhor solução é mudar a origem da consulta.

  Hoje o fluxo é:

  Terminal aberto → API REST → nova conexão SSH → novo canal SFTP → listar diretório

  Essa nova conexão é o provável motivo da demora. O terminal já está conectado, mas o autocomplete inicia outra autenticação SSH do zero.

  Recomendação principal:

  Terminal aberto → WebSocket existente → canal SFTP da mesma conexão SSH → listar diretório

  O gateway pode abrir o canal SFTP uma única vez, sob demanda, e reutilizá-lo durante toda a sessão. Isso traz:

  - resposta normalmente em poucos milissegundos após a primeira consulta;
  - reutilização de autenticação, bastion e rota já validados;
  - funcionamento com credenciais temporárias informadas ao abrir o terminal;
  - menos conexões e menor carga no host;
  - isolamento por sessão;
  - encerramento automático junto com o terminal.

  Também recomendo um comportamento progressivo:

  1. Mostrar imediatamente sugestões já conhecidas pelo cache.
  2. Consultar o host em segundo plano pela conexão existente.
  3. Atualizar a lista quando a resposta chegar.
  4. Não exibir um popup apenas com “Buscando”.
  5. Se o host demorar, fechar silenciosamente o popup ou mostrar um pequeno indicador não bloqueante.
  6. Manter cache por sessão e diretório, invalidando após mkdir, mv, rm etc.

  Podemos ainda “aprender” caminhos durante o uso:

  - diretório atual por OSC 7;
  - diretórios anteriormente visitados;
  - resultados SFTP já consultados;
  - caminhos aceitos pelo usuário;
  - resultados explícitos de ls, com muito cuidado para não interpretar qualquer saída como estrutura de arquivos.

  Eu não usaria ls oculto nem enviaria Tab para o shell. Isso poderia:

  - interferir no comando digitado;
  - produzir saída na auditoria;
  - disparar funções ou aliases;
  - causar efeitos inesperados em shells diferentes.

  A arquitetura que considero ideal é:

  Autocomplete
      ├── cache local imediato
      ├── índice aprendido da sessão
      └── consulta path_list pelo WebSocket
               └── SFTP reutilizado da conexão SSH ativa

  Além disso, a mensagem de demora deveria ser removida do fluxo normal. O autocomplete é um auxílio: se não houver resposta rápida, ele deve simplesmente
  continuar sem atrapalhar a digitação.

  Minha recomendação é implementar agora o protocolo path_list/path_result no WebSocket, reutilizar um canal SFTP dentro de SshSession e manter a API REST atual
  apenas como fallback para o navegador de arquivos. Essa mudança resolve a causa estrutural, não apenas aumenta o timeout.

  ## Terminal

  ### 1. Barra contextual da sessão

  Mostrar permanentemente, sem poluir:

  - host e IP;
  - pasta corporativa;
  - ambiente: produção, homologação ou desenvolvimento;
  - método de conexão;
  - bastion ou agente utilizado;
  - latência;
  - usuário SSH;
  - indicador de sessão gravada ou compartilhada.

  Para hosts de produção, pode existir uma borda ou etiqueta diferenciada, sem depender apenas de cor.

  Personalizável pelo usuário:

  - modo compacto ou detalhado;
  - campos que deseja visualizar;
  - ocultar IP;
  - exibir latência;
  - destacar produção;
  - formato do título da aba: nome, IP, pasta ou ambiente.

  ### 2. Workspace recuperável

  Atualmente, recuperar o contexto de trabalho teria bastante valor:

  - salvar abas abertas;
  - salvar divisão dos painéis;
  - nomes personalizados;
  - painel lateral aberto;
  - diretório SFTP atual;
  - restaurar manualmente na próxima entrada.

  A restauração não deve conectar automaticamente sem confirmação, especialmente em produção. Poderia mostrar:

  > Seu último workspace possuía 6 sessões. Deseja reabri-las?

  Personalizável:

  - não salvar;
  - perguntar ao entrar;
  - restaurar abas desconectadas;
  - restaurar e conectar automaticamente apenas hosts não produtivos.

  ### 3. Modo de foco e densidade

  Já existem modos de visualização, mas podem virar perfis claros:

  - Operação: terminal amplo e pouca interface.
  - Administração: terminal + SFTP.
  - Automação: terminal + snippets.
  - Diagnóstico: terminal + IA + métricas.
  - Colaboração: terminal + participantes.

  O usuário escolheria o perfil padrão e poderia trocar rapidamente durante a sessão.

  ### 4. Segurança contextual de comandos

  Antes de enviar comandos potencialmente destrutivos:

  - detectar rm -rf, mkfs, shutdown, reboot, alterações de firewall, banco ou permissões amplas;
  - mostrar host, ambiente e comando;
  - exigir confirmação;
  - permitir copiar ou editar;
  - registrar a decisão na auditoria.

  Personalizável pelo usuário:

  - confirmar apenas em produção;
  - confirmar sempre;
  - não confirmar comandos comuns;
  - manter lista pessoal de comandos confiáveis.

  A organização precisa poder impor uma política mínima que o usuário não consiga desativar.

  ### 5. Diagnóstico da conexão

  Um pequeno painel “Qualidade da sessão” poderia apresentar:

  - latência atual e p95;
  - tempo para conectar;
  - reconexões;
  - desconexões;
  - quantidade de dados;
  - bastion/agente em uso;
  - último motivo de fechamento;
  - WebSocket, SSH e SFTP individualmente.

  Isso ajudaria muito a separar problema do navegador, NodeAccess, agente, bastion ou servidor remoto.

  Personalizável:

  - mostrar latência na barra;
  - alertar acima de determinado valor;
  - sugerir reconexão;
  - manter painel oculto por padrão.

  ## Snippets

  ### 1. Parâmetros tipados

  Permitir criar snippets como:

  systemctl restart {{service}}
  tail -n {{lines}} {{log_file}}

  Antes de executar, o NodeAccess apresentaria um formulário com:

  - texto;
  - número;
  - seleção;
  - host;
  - arquivo remoto;
  - secret;
  - confirmação;
  - valor padrão.

  Isso reduz duplicação e erros de digitação.

  ### 2. Preview antes da execução

  Exibir claramente:

  - comando final;
  - host de destino;
  - quantidade de etapas;
  - secrets que serão resolvidos;
  - comandos potencialmente perigosos;
  - se será enviado para uma ou várias sessões.

  Secrets devem aparecer mascarados no preview.

  Personalizável:

  - sempre mostrar preview;
  - mostrar apenas para sequências;
  - mostrar apenas em produção;
  - executar snippets confiáveis diretamente.

  ### 3. Favoritos, recentes e atalhos pessoais

  Cada usuário poderia:

  - favoritar snippets;
  - ordenar favoritos;
  - criar atalhos próprios;
  - ocultar snippets que não utiliza;
  - selecionar a visualização plana ou agrupada;
  - definir snippets mais usados por host, tag ou pasta.

  ### 4. Compatibilidade e requisitos

  Um snippet poderia declarar:

  - Linux ou Windows;
  - shell esperado;
  - comandos necessários;
  - privilégio root;
  - tags ou grupos permitidos;
  - timeout;
  - código de saída esperado.

  Antes da execução, o NodeAccess verificaria compatibilidade e explicaria por que não pode executar.

  ### 5. Execução assistida e resultados

  Para sequências:

  - progresso por etapa;
  - etapa atual;
  - pausar ou cancelar;
  - sucesso, falha ou timeout;
  - saída relevante;
  - opção “tentar novamente a partir desta etapa”.

  Não recomendo executar automaticamente etapas destrutivas após um erro sem nova confirmação.

  ## SFTP

  ### 1. Central de transferências

  É provavelmente a melhoria de maior retorno imediato:

  - fila de uploads e downloads;
  - progresso individual e total;
  - velocidade;
  - tempo estimado;
  - concluído, cancelado ou com erro;
  - tentar novamente;
  - limpar concluídos;
  - continuar usando o terminal durante a transferência.

  Personalizável:

  - quantidade de transferências paralelas;
  - fechar painel ao concluir;
  - notificação sonora ou visual;
  - manter histórico;
  - confirmar arquivos grandes.

  ### 2. Drag-and-drop

  Permitir arrastar arquivos:

  - do computador para a pasta remota;
  - entre pastas remotas;
  - para uma área explícita de upload.

  Deve existir preview do destino e tratamento de conflito:

  - substituir;
  - manter os dois;
  - pular;
  - aplicar a todos.

  ### 3. Editor remoto aprimorado

  O serviço já possui leitura, escrita, hash, backup, diff e restauração. A interface pode explorar melhor isso:

  - editor com syntax highlighting;
  - indicação de alterações não salvas;
  - comparação antes/depois;
  - detecção de edição concorrente;
  - backup automático;
  - restaurar versão anterior;
  - validação opcional antes de salvar, como JSON/YAML.

  Personalizável:

  - quebra de linha;
  - tamanho da fonte;
  - tema;
  - backup automático;
  - confirmação antes de sobrescrever;
  - editor somente leitura para arquivos grandes.

  ### 4. Operações em massa

  - selecionar vários arquivos;
  - download compactado;
  - mover;
  - excluir;
  - alterar permissões;
  - pesquisa na pasta;
  - filtro por tipo, data e tamanho.

  Exclusão e alteração de permissões precisam de confirmação clara.

  ### 5. Favoritos e caminhos recentes

  Por usuário e, opcionalmente, por host:

  - /var/log;
  - /etc/nginx;
  - diretório da aplicação;
  - home do usuário;
  - últimos caminhos acessados.

  Também seria útil abrir o SFTP automaticamente no diretório atual do terminal quando o shell expuser essa informação.

  ## Compartilhamento de sessão

  ### 1. Assistente de compartilhamento

  Ao criar um compartilhamento, mostrar:

  - quem poderá acessar;
  - somente visualização ou possibilidade de solicitar controle;
  - validade;
  - se clipboard é permitido;
  - se a sessão está sendo auditada;
  - host e ambiente envolvidos.

  ### 2. Permissões mais granulares

  Além de viewer e controle temporário:

  - visualizar somente;
  - solicitar controle;
  - controle permitido automaticamente;
  - copiar saída;
  - usar clipboard;
  - usar snippets;
  - acessar SFTP;
  - visualizar dados sensíveis.

  A configuração padrão deve ser conservadora: somente visualização, sem SFTP e sem clipboard compartilhado.

  ### 3. Presença e eventos

  Mostrar uma linha temporal simples:

  - usuário entrou;
  - solicitou controle;
  - controle concedido;
  - executou entrada;
  - controle revogado;
  - saiu.

  O proprietário precisa ter um botão sempre visível de “Retomar controle”.

  ### 4. Compartilhamento interno direcionado

  Além de copiar link:

  - selecionar usuário ou grupo do NodeAccess;
  - enviar convite interno;
  - mostrar notificações;
  - listar sessões compartilhadas comigo;
  - revogar todas as sessões abertas.

  ### 5. Anotações durante atendimento

  Em sessões de suporte:

  - adicionar notas com horário;
  - marcar “problema identificado”;
  - registrar solução;
  - exportar resumo da sessão sem expor secrets.

  ## Preferências que fazem sentido por usuário

  Eu adicionaria uma seção “Terminal e produtividade” no perfil:

  - perfil de workspace padrão;
  - restauração do workspace;
  - posição e largura do painel lateral;
  - painel inicial: arquivos, snippets ou nenhum;
  - exibição de latência;
  - destaque de ambiente produtivo;
  - formato do nome das abas;
  - confirmação de multiline paste;
  - confirmação de comandos sensíveis;
  - autocomplete;
  - IA;
  - sugestões de caminhos remotos;
  - histórico pessoal;
  - favoritos de snippets;
  - preview antes de snippets;
  - comportamento de conflitos SFTP;
  - transferências paralelas;
  - notificações;
  - backup automático do editor;
  - modo padrão de compartilhamento;
  - duração padrão de compartilhamento.

  ## O que não deve ser apenas escolha do usuário

  Algumas decisões pertencem à política do tenant:

  - obrigatoriedade de gravação;
  - comandos bloqueados;
  - confirmação de comandos críticos;
  - acesso ao SFTP;
  - tamanho máximo de upload;
  - clipboard em sessão compartilhada;
  - validade máxima do compartilhamento;
  - concessão de controle;
  - retenção de auditoria;
  - mascaramento de secrets;
  - possibilidade de restaurar sessões automaticamente;
  - uso de IA com conteúdo do terminal.

  A regra ideal é: o tenant define limites; o usuário personaliza o comportamento dentro deles.

  ## Ordem que eu adotaria

  1. Central de transferências SFTP.
  2. Barra contextual e destaque de ambiente.
  3. Snippets parametrizados com preview.
  4. Recuperação de workspace sem conexão automática.
  5. Diagnóstico de qualidade da sessão.
  6. Assistente e permissões de compartilhamento.
  7. Favoritos, históricos e caminhos recentes.
  8. Editor SFTP aprimorado e operações em massa.

  Essa sequência entrega produtividade perceptível sem aumentar cedo demais a complexidade do gateway SSH. A análise também confirma que as preferências devem continuar no
  contrato de usuário já existente em packages/shared/src/schemas/user-preferences.schema.ts, enquanto políticas obrigatórias devem permanecer no tenant.
